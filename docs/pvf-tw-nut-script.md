# TW 明文 Squirrel 脚本（.nut）解码与代码高亮（70TW）

## 1. 问题现象

`PVF/70TW/Script.pvf` 的 `sqr/init_character.nut` 等明文 Squirrel 脚本在 PVF 编辑器中存在两个问题：

1. **注释乱码**：`//` 注释内容显示为无意义汉字噪声（如「嚙踝蕭」），部分外部工具按 EUC-KR 解码则显示「占쏙옙」类字符，均不可读；
2. **无代码风格高亮**：`.nut` 在 TW 层 `dataType` 恒为 1，编辑器 `highlightMode` 判定为「pvf」模式，按 PVF token 脚本语法（`#` 注释 / 反引号字符串 / `[标签]`）渲染 Squirrel 代码，关键字、字符串、数字均不着色，且 `[` `]` 等字符可能被误染为标签色。

## 2. 字节级定性（已用实际文件字节验证）

### 2.1 样本留存

按「解析异常样本留存（PVF）」门控，自归档数据区一次性切片留存**未解密原始流**：

| 项目               | 值                                                                    |
| ------------------ | --------------------------------------------------------------------- |
| 归档内路径         | `sqr/init_character.nut`                                              |
| 留存位置           | `test/70TW/sqr/init_character.nut`                                    |
| checksum           | `0x126DB5C1`                                                          |
| dataSize / trueLen | 2906 / 2908 字节（4 字节对齐）                                        |
| 归档内偏移         | dataOffset 47906296 + 数据区基址 14640864                             |
| 现场还原方式       | `pvfDecryptTw(字节流, TW_DECRYPT_KEY, 0x126DB5C1)` 后截取前 2906 字节 |

### 2.2 明文形态与损坏定性（2026-09-10 修正：混合编码流）

- 还原后头部字节 `0d 0a 66 75 6e 63 74 69 6f 6e ...`（`\r\nfunction ...`）：**明文文本**，无 `#PVF_File` 前缀、无 `0xB0 0xD0` token 魔数，代码部分为 ASCII。
- 注释区字节为**混合编码流**：大部分原始 EUC-KR 谚文字节已被 UTF-8 净化为 `EF BF BD`（U+FFFD），但**少量「恰好构成合法 UTF-8 序列」的 EUC-KR 双字节对（高字节 `C2`~~`DF` + 低字节 `80`~~`BF`）原样残留**。样本（`sqr/init_character.nut`）统计：`EF BF BD` 序列 192 处 + 残留对 31 处。
- 净化机制还原：第三方打包工具以 UTF-8 解码器读取原 EUC-KR 韩文注释——高字节 `B0`~~`BF` / 低字节 `C0`~~`FE` 的对与越界序列非法 → U+FFFD；高字节 `C2`~~`DF` 且低字节 `80`~~`BF` 的对恰好合法 → 被解码为 U+0080~U+07FF 的拉丁/西里尔占位字符原样保留字节；随后以合法 UTF-8 写回归档（这解释了 §2.3 的 95/95 严格 UTF-8 成功）。
- **残留对可精确恢复**（已用实际字节验证）：`C5 B8`→`타`、`C4 B5`→`캔`、`C3 B3`→`처`、`C4 B3`→`캐`、`C6 AE`→`트`、`C8 A3`→`호`、`C7 B4`→`풔`、`C5 A9`→`크`；落在 KS 汉字区（`CA`~`DF` 高字节）的对按 CP949 解出对应汉字（如 `D2 B6`→`秊`、`CE BC`→`關`）。WHATWG euc-kr 表对用户定义区（如 `C9 B6`）映射到私有区（U+E0xx）——属无法还原的 UDC 残留，按损坏（U+FFFD）呈现。
- **定性**：`EF BF BD` 部分为数据本体损坏、信息不可逆丢失（非解析错误），与 `event/event.kor.str`（`docs/pvf-tw-format.md` §8.7）同源同性质，任何展示层恢复均为伪造；**残留双字节对部分语义完整、可精确恢复**——展示层按其原始字节以 CP949（euc-kr）解读，恢复原谚文/汉字，属正确解读而非净化改写。

### 2.3 全量编码分布（70TW 归档 95 个 .nut）

对归档内全部 `.nut` 明文做严格编码判定（`utf-8` / `big5` / `gbk` 依次 fatal 解码）：

| 分类                       | 数量 | 说明                         |
| -------------------------- | ---- | ---------------------------- |
| 严格 UTF-8 成功、无 U+FFFD | 77   | 纯 ASCII 或完好 UTF-8 注释   |
| 严格 UTF-8 成功、含 U+FFFD | 18   | 注释净化损坏（含 §2.1 样本） |
| 仅 big5 / 仅 gbk 可解码    | 0    | 无反例                       |

结论：**70TW 的 `.nut` 明文全部为 UTF-8 字节流，无 Big5/GBK 反例**，按 UTF-8 优先解码规则无副作用。

### 2.4 韩文注释可恢复性全量验证（2026-09-10 修正）

对 95 个 `.nut` 全部 `//` 注释行逐行统计（严格 UTF-8 解码后判定；**初版统计将「谚文残留 + U+FFFD 混合行」整体归入损坏，结论「完好韩文 0 行」表述失准——混合行中残留对部分可恢复，本节为修正后的定性**）：

| 注释行分类         | 行数                | 说明                                                                                                                         |
| ------------------ | ------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 含 U+FFFD          | 75（16 个文件）     | 韩文注释净化损坏形态（大部分谚文字节已不可逆丢失）                                                                           |
| 同时含可恢复残留对 | 17（全部含 U+FFFD） | 残留 `C2`~~`DF`/`80`~~`BF` 对，恢复后可读谚文/汉字（`타`、`캔`、`처`、`캐`、`트`、`호` 等）                                  |
| 含完好 CJK 汉字    | 10                  | 第三方技能打包者的繁体署名水印（`swordman_throw.nut`、`ap_skill38.nut` 等，后加的完好 UTF-8 注释，无痕迹字符、不受恢复影响） |
| 纯 ASCII           | 88                  | 代码标记类注释                                                                                                               |
| 空（仅 `//`）      | 10                  | —                                                                                                                            |

- 全量字符级恢复原型统计：恢复输出谚文 169 + 汉字 220 + 私有区/UDC 残留 5（按 U+FFFD 呈现）+ 替换符 0；**含残留对的 17 个文件全部同时含 U+FFFD**（零漏网），「含 U+FFFD」即可作为恢复门控，纯 UTF-8 文件（77 个，含水印）无痕迹字符不受影响。
- 证据链：① 大部分谚文字节（高字节 `B0`~`BF`）净化后不可逆，任何展示层恢复均为伪造；② 残留对语义完整且按 CP949 解码得到正确谚文/汉字，与第三方工具（CP949 解码）所见的可读片段（`1타 캔`、`처…캐…트…호풔`）一一对应；③ 完好繁体水印注释的存在证明「UTF-8 编码的注释可完整存活」，排除「解码方式选错导致韩文不可读」的可能。

## 3. 解决方式

### 3.1 解码（`src/utils/pvfToolTw.js`）

- `decodeContent` 内 `.nut` 分流至 `_twDecodeNutText`，按**编码形态二分**（2026-09-10 经用户确认为「按原始字节解析、不做替换净化」的展示原则）：
    1. **纯 UTF-8 文件**（严格 UTF-8 成功且不含 U+FFFD，77 个，含第三方繁体水印注释）：按 UTF-8 直解展示；
    2. **净化混合流文件**（严格 UTF-8 成功但含 U+FFFD，18 个）与严格解码失败文件的防御回落：按**原始编码 CP949（euc-kr）直解**展示——残留 EUC-KR 对自然显示原谚文 / KS 汉字（`타`、`캔`、`처`、`캐`、`트`、`호`、`풔`、`크`、`秊`、`關` 等，与字符级恢复方案结果一致），净化损坏字节（`EF BF BD` 循环）自然显示为「占쏙옙」（CP949 对该循环的标准映射，与外部参照工具形态一致）；解码器对孤立字节产生的少量 U+FFFD 为固有行为，**不再叠加任何恢复 / 净化 / 替换处理**。
    3. **替换符密度门控（防误判）**：严格 UTF-8 成功但含 U+FFFD 的文件，先以 CP949 **试解码**并统计替换符占比——占比低（净化流的孤立字节固有替换，实测样本 4/1064 ≈ 0.4%，阈值 5%）→ 判定为净化流，走 CP949 直解；占比高（UTF-8 语义文件，如「旧版保存或外部工具产生的 UTF-8 + 零星替换符」，实测 ~50%）→ 保持 UTF-8 直解原样呈现，避免把 UTF-8 字节当 CP949 二次误解为乱码。
- 展示形态选择记录：「字符级恢复 + U+FFFD」与「CP949 直解 + 占쏙옙」两方案的可读内容完全一致（同一批残留字节），差异仅在损坏处形态；经用户确认为 CP949 原始形态。
- **三 / 四字节残留边界（已验证、不单独处理）**：净化流中另存在 UTF-8 三 / 四字节形态的 EUC-KR 残留（如 `E2 BA BB`→U+2EBB、`EE BA A5`→U+EEA5 私有区），95 个文件共 17 处（11 个文件），随 CP949 直解自然呈现（产出 KS 汉字 + 替换符 / 私有区占位），不单独恢复。
- `EF BF BD` 损坏部分原样呈现（U+FFFD），不做任何变换（门控）。

### 3.2 编码 / 回写（`src/utils/pvfToolTw.js` + 新增 `src/utils/euckrEncoder.js`）

- 修复现存隐患：`encodeContent` 对非 .lst 文件一律走 `encodeTwToken`，`.nut` 编辑保存会被误 token 化而损坏。新增 `.nut` 分支：不做 token 化，按**显示文本的编码语义**对称回写（2026-09-10 二次修正——此前「U+FFFD→`?` 后 UTF-8 回写」方案改变了文件编码语义，外部 CP949 工具读取全乱，已废弃）：
    - **净化混合流文本**（含 U+FFFD 或谚文音节，CP949 直解语义）：经 **CP949 反查编码**回写。新增 `src/utils/euckrEncoder.js`（对齐 `gbkEncoder.js` 模式：加载时以 `TextDecoder("euc-kr")` 枚举双字节空间（高 `0x81`~~`0xFD` × 低 `0x40`~~`0xFE` 除 `0x7F`）构建反查表，**排除 U+FFFD 映射**；导出 `encodeEUCKR` / `euckrCode`）。可编码字符（谚文 / KS 汉字 / 损坏标记「占쏙옙」/ UDC 残留私有区）逐字节还原原字节——**交织对称性**：`EF BF BD` 循环解码为「占쏙옙」循环，字符反查编码精确还原字节（实测 roundtrip 2906B ↔ 2906B，仅 4 个孤立字节替换符不可逆、显式降级 `?` 0x3F，沿用 `encodeGBK` 惯例）。保存后文件保持 CP949 字节语义：外部 CP949 工具与本仓（密度门控 → CP949 直解）读回显示一致。
    - **纯 UTF-8 文本**（无 U+FFFD 且无谚文音节，繁体水印 / 纯 ASCII）：`encodeText(text, "utf-8")` 原样回写，与源明文逐字节一致。
- 展示层文本经 `_normalizeLines` 行尾归一化（`\r\n` → `\n`，与既有 `#PVF_File` 明文行为一致），编辑保存的行尾按展示层 `\n` 写回，属既有明文回写惯例。

### 3.3 代码风格高亮（`src/utils/pvfHighlight.js` / `src/components/PvfEditor.vue`）

- `pvfHighlight.js` 新增 Squirrel 语言定义 `registerNutLanguage(hljs)`（注册名 `squirrel`，highlight.js 无内置同名语言）：`//` 与 `/* */` 注释、`"..."` 与 `'...'` 字符串（含转义）、Squirrel 关键字（function/local/if/else/for/foreach/while/do/class/extends/constructor/return/break/continue/in/base/this/null/true/false/switch/case/default/try/catch/throw/typeof/instanceof/delete/static/const 等）、数字（十进制 / 十六进制 `0x` / 浮点）、函数名（title）、**new-slot 操作符 `<-`（operator，如 `sqr/dnf_enum_header.nut` 的 `LANDTYPE_POISONSWAMP <- 3` 枚举赋值）**。
- **token 覆盖扩充（2026-09-10，标识符层级着色）**：原规则仅覆盖注释 / 字符串 / 关键字 / 数字，占比最大的标识符一概无色，高亮层次感弱。新增五类规则：全大写常量 / 枚举名（constant，如 `LANDTYPE_POISONSWAMP`）、函数调用名（标识符后紧跟 `(`）与 `function` 定义处函数名统一 `title.function`（定义处规则在前优先命中，定义 / 调用视觉一致）、`class` / `extends` 后类名（`title.class`）、`.` 后成员属性（`property`，置于调用规则前，成员链统一浅蓝）、literal（`null` / `true` / `false` 经 keywords literal 输出独立 `hljs-literal` 类）。
- **变量参数名着色（2026-09-10 增补）+ 关键字排除修复**：函数参数名（`function f(a, b)` 括号内标识符，`params` 容器内 `variable` 类）、`local` 声明变量与其余裸标识符以**兜底规则统一着 `variable` 类**（浅蓝 `#9cdcfe`，与 property 同系——TextMate 版参考实现同款思路：裸标识符统一变量色，更高优先级规则先命中）。**hljs contains 规则优先于 keywords 检测的实测结论**（ident 兜底规则可命中任意位置，keywords 将永不生效；`if (` / `for (` 等控制流关键字此前即被调用规则误染为函数色，既有断言靠其它关键字凑数未暴露）——调用规则与兜底规则以**负向先行排除关键字与 literal**，keywords 检测恢复正常接管（`if` / `for` / `local` / `function` 等回归关键字色）；规则链优先级：注释 / 字符串 / 数字 / params / operator / title.function（定义 + 调用，排除关键字）/ title.class / property / constant / variable 兜底（排除关键字与 literal）。
- `PvfEditor.vue`：`highlightMode` 对 `.nut` 返回 `"nut"`；`updateHighlight` 与 `_renderHighlighted` 新增 `"nut"` 分支调用 `hljs.highlight(text, { language: "squirrel" })`，不叠加 PVF 标签注解（`annotateTagSpans` / `annotateRefs` / `grayLstNames`）；样式段新增 `.hljs-operator` 灰色（`#9a9a9a`，与既有 `.hljs-pvf-name` / `.hljs-pvf-bin-text` 灰一致），枚举赋值的 `<-` 弱化为灰色以突出名字与值；token 覆盖扩充对应样式新增 `.hljs-constant`（金黄 `#d7ba7d`）、`.hljs-title.function_`（黄 `#dcdcaa`）、`.hljs-title.class_`（青绿 `#4ec9b0`）、`.hljs-property`（浅蓝 `#9cdcfe`，与既有 `.hljs-title` 同系）、`.hljs-literal`（蓝 `#569cd6`）、`.hljs-variable`（浅蓝 `#9cdcfe`，参数 / 局部变量 / 裸标识符；`.hljs-params` 容器不着色，由子元素 variable 着色），形成常量 / 函数 / 类 / 成员四层色阶。
- `applyFormatting` 对 `.nut` 跳过 PVF token 文本重排（Squirrel 源码自带缩进，重排会破坏版式）；`.nut` 的缩进格式化另行经工具栏「格式化」按钮显式触发，见 §3.4。
- 保存链路自然受益：`.nut` 的 `highlightMode` 非 `"pvf"`，`stageChange` 中的 PVF 语法校验自动跳过；`runValidation` 在 TW 层本就停用。

### 3.4 Squirrel 缩进格式化（2026-09-10，显式触发）

- 参考项目：外部开源项目 `vscode-squirrel`（Bitbucket `marcinbar91/vscode-squirrel`，MIT）。其格式化实现为「移植版 js-beautify（`FormatterOptions`，默认 `indent_size: 4` / 空格字符）完整重排」+「轻量缩进重排 `formatSquirrelIndent`（Tab 单级、行内 `{`/`}` 计数、switch 内 `case`/`default` 额外层级）」。登记性质：仅作对照参考，upstream 演进不自动生效。同作者的 `vscode-squirrel_linter` 为官方编译器驱动的语法 linter，无格式化内容，不作排版参考。
- 参考实现的已知缺陷（本仓实现予以修正）：① js-beautify 将 new-slot `<-` 拆为 `< -`，其输入时路径的修正 `replace("< -", "<- ")` 不带全局标志会漏修多处枚举赋值，Format Document 路径无修正；② `formatSquirrelIndent` 行内裸计数 `{`/`}`，字符串字面量与注释内的花括号会带偏层级；③ `@"..."` verbatim 多行字符串（Squirrel 特有、无转义、可含真实换行）在 JS 模式重排下会被破坏。
- 本仓实现（新增 `src/utils/pvfNutFormat.js`，导出 `formatNutText(text)`）：**Tab 1 级缩进**；**token 级流式状态机整段扫描**——字符串（`"..."` / `'...'` / `@"..."` verbatim）与 `//` / `/* */` 注释内容不参与花括号计数与层级判定（修正缺陷 ①②③）；`case` / `default` 输出层级 = switch 层 + 1、case 体行 = switch 层 + 2（对齐参考规则）；行首以 `}` 开始先减层再输出（闭合与开括号左对齐语义）；空行保持、行尾空白清理、行尾 LF（展示层既有惯例）；格式化幂等（重复应用结果不变）。
- **行首闭合与行内计数互斥（2026-09-10 修正）**：行首首个 `}` 的层级效应由行首减层承担一次，不再计入行内花括号净变化（初版两处重复扣层，嵌套闭合链每层多扣一级导致层级错位——函数格式化金样本抓出，见 §6）；错层表现为深层闭合行与闭合后的函数体语句（如 `return true;`）被顶格输出。修正后对齐用户建议的函数格式化样例：函数定义顶格、函数体 1 级、嵌套块逐级、闭合与开括号左对齐、函数间 / 语句组间 / `{` 后空行原样保留、单行 `if (...) return ...;` 保持同行。
- **悬挂单语句体缩进（2026-09-10 二次修正）**：省略 `{}` 的控制流单语句体（如 `if (!obj)` 换行后接 `return -1;`）——下一非空代码行按悬挂体缩进一级（连续悬挂链逐级递增：`if` 行体、`else` 行等，悬挂判定 = 悬挂词（if / else / for / foreach / while，`else` 豁免行尾判定）+ 行内花括号净变化为 0 + 行尾有效字符为 `)` 或裸 `else`；单行带体的 `if (a) return b;` 不悬挂（行尾 `;`）；跨空行断链）。
- **独立 `{` 吸附（2026-09-10 二次修正，三次修正带空格）**：独立成行的 `{`（纯 `{` 代码行）吸附到上一条非空代码行行尾（Allman → K&R），仅当上一行满足「代码行（非注释 / verbatim 延续行）+ 行尾有效字符为 `)` + 行未以注释收尾」（如 `function create_CreatorMage(obj)` + 独立 `{` → `function create_CreatorMage(obj) {`，吸附后前置一个空格，对齐用户样例 `function requestBuy(...) {`；2026-09-10 三次修正——初版无空格 `){`，经用户确认为带空格 `) {`）；吸附行花括号计数并入吸附目标行，独立 `{` 连续两行不重复吸附；其余情况保持独立 `{` 行并正常缩进。
- **空行压缩（2026-09-10 增补）**：格式化时连续空行（≥2）压缩为恰好一个空行（文件开头 / 中间 / 结尾同样适用）；块注释 / verbatim 字符串延续期间的空行属字符串 / 注释内容，逐字保留不压缩。悬挂体链的空行断链语义不变（压缩后空行仍断链）。
- **函数间空行保证（2026-09-10 增补，注释吸附同批）**：顶层 `function` 定义行与其上一条非空代码行之间至少一个空行（已有一个则不插入，多个由空行压缩规则归一）；**函数注释与 `function` 保持一体**——注释块紧贴函数行、两者之间不插入空行，且注释块与 `function` 之间已有的空行**删除**（2026-09-10 注释吸附增补）；函数上方独立注释块随函数整体分隔——空行插入注释块上方（如 `}` / `// 注释` / `function f()` → `}` / 空 / `// 注释` / `function f()`；`}` / `// 注释` / 空 / `function f()` → `}` / 空 / `// 注释` / `function f()`，注释与函数间空行删除）；嵌套函数（函数体内 `function`，level ≠ 0）不处理；文件开头的函数定义与其头注释不处理。
- **else 吸附（2026-09-10 增补）**：`else` 行（含 `else if (...)`，行首词为 `else`）紧贴上一条非空代码行行尾吸附——上一行行尾有效字符为 `}` 时吸附为 `} else`（带空格）；其后的独立 `{` 行吸附到 else 行尾（吸附条件扩展：上一行行尾有效字符为 `)` **或**行首词为 `else`），合成 `} else {`。`}else{` / `} else {` 单行紧凑形态自洽（行内文本不做空格重排，仅缩进修正）；悬挂 `else` 体（省略 `{}`）不受影响。
- **else 吸附内容保留（2026-09-11 修正，缺陷修复）**：此前吸附只拼接关键字字面量 `} else`，**丢弃该行 `else` 之后的全部内容**——Allman 风格 `}` / `else if (cond)` / `{` 三行形态经格式化后条件整体丢失，输出退化为 `} else {`（多条分支相互混淆，语义被破坏）。现改为把 else 行的**剩余原文**（`else` 之后的文本，先经 `padOperatorSpacing` 归一运算符空格）一并拼接，得 `} else if (cond) {`；`else` 单独成行时剩余为空，输出与既有形态一致。断言见 §4 表（`formatNutText` else-if 链，含 `else` 单行与 `else{` 紧凑形态）。
- **嵌套区块缩进（2026-09-10 增补，显示缩进栈方案）**：缩进层级改为**显示缩进栈**——每个已开 `{` 区块记录其开括号行的显示缩进（普通块 / `switch` 块 / 悬挂体内 `{` 均入栈），闭合 `}` 行与对应开括号行**左对齐**（取栈顶显示缩进，不再按花括号层级计算）；`case` / `default` 行 = 所属 `switch` 块（栈顶向下最近的 switch frame，嵌套时逐层恢复）显示缩进 + 1，case 体行 = + 2，嵌套 `switch` / `if` 等区块同理逐层推进。此修正解决：嵌套 `switch` 时内层 `case` 与外层 `case` 体错位、内层 `}` 闭合行与内层 `switch` 行不对齐、内层闭合后外层 `case` 体 `break` 行层级错位（单值 `switchLevel` 被嵌套覆盖后未恢复的历史缺陷）。
- **运算符空格规范化（2026-09-10 增补）**：代码行内二元运算符两端缺失空格时补**单个空格**（已有空格保持、不重复插入）——二元运算符集合：`+`、`-`、`*`、`/`、`%`、`^`、`&&`、`||`、`==`、`!=`、`<=`、`>=`、`<`、`>`、`=` 与 new-slot `<-`（多字符 token 优先识别，`<=` / `>=` / `==` / `!=` 不被单字符 `<` / `>` / `=` 拆开）。**一元形态不补**：`+` / `-` 的前一非空白 token 非操作数（如 `-1`、`x = -1`）按一元处理、前后均不补；`++` / `--` / `!` 不参与规范化（`i++`、`!obj` 原样）；`.` 成员点不处理。字符串（`"..."`、`'...'`、`@"..."`）与 `//`、`/* */` 注释内容逐字保留（token 级状态机跳过）；仅「格式化」显式触发时生效（语义边界同上）。
- **语义边界（不自动）**：`.nut` 明文现行原则为「按原始字节解析、原样回写」（§3.1 / §3.2）；缩进格式化**仅经编辑器工具栏「格式化」按钮显式触发**（对当前编辑文本应用并进入脏态，再经既有保存链写盘），文件加载 / 导入 / 切换编码不自动重排（`applyFormatting` 对 `.nut` 维持跳过）。格式化保存后文件字节真实变化——Squirrel 语义与编码分支判定不变（仅重排 ASCII 空白与行首缩进，字符串 / 注释内容逐字保留），不再与原文逐字节一致（2026-09-10 用户确认接受）。

### 3.5 函数体花括号折叠（2026-09-11，折叠为纯展示行为、折叠态仍可编辑，参照 VS Code 编辑器）

- 交互参照 VS Code 编辑器：`.nut` 编辑器中函数体 / 控制流 / 类体等 `{}` 区块可折叠。折叠为**纯展示行为**——不改动文本模型（不触碰 `editText` / `originalText`），仅隐藏折叠区间内的行；行号沿用原始行号（折叠后自然跳号），与 VS Code 一致。（注意区分措辞：**折叠动作本身**不改文本；**折叠态下**被隐藏的行不可编辑、非隐藏区照常可编辑，见下文「渲染与交互」「折叠态编辑合并」——「折叠视图为只读」的旧表述已废弃。）
- 折叠后版式（VS Code 对照结论）：与 VS Code 默认的缩进折叠一致，折叠区**不包含闭括号行**——VS Code 的折叠区「起于缩进增大的行、止于缩进回落到同级或更浅之前的最后一行」，闭括号行与原行同级因而不属于折叠区。据此本仓折叠后可见 **开括号行（行尾追加 `⋯` 折叠占位符）+ 闭括号行**，仅隐藏两者之间的行；占位符字符取 VS Code 同款 `⋯`（U+22EF），并支持点击展开（VS Code 折叠占位符可点击）。
- 与 PVF 块标签折叠的关系（**不沿用**）：PVF 块标签折叠采用「文本占位」机制（把区块行从编辑文本中合并为一行占位符、保存前 `unfoldAll` 还原，会改变行号与文本状态）；nut 折叠独立实现，**不共用** `folds` / `foldableLines` / `foldedLineSet` / `unfoldAll` / `toggleFold` 等 PVF 折叠基础设施，折叠状态与文本完全解耦。
- 折叠判定（`src/utils/pvfNutFormat.js` 新增 `findNutFoldRanges(text)`）：token 级状态机扫描（与格式化器同款状态机语义）——`{` 与 `}` 逐行配对，仅「闭括号行 - 开括号行 ≥ 2」即开闭行之间**至少存在一行可隐藏内容**的跨行区块可折叠（与 VS Code 折叠区「至少包含一行」的下限一致；空体 / 相邻开闭行即 `{` 下一行就是 `}` 不产生折叠区）；字符串（`"..."` / `'...'` / `@"..."` verbatim）与 `//` / `/* */` 注释内的花括号不参与配对；同行 `{ ... }`（如 `function f() { return 1; }`）不折叠；未闭合的 `{` 不产生折叠区；同一行存在多个 `{` 时取该行最外层区块（首个 `{` 的配对 `}` 所在行）。
- 折叠状态（`src/utils/pvfNutFormat.js` 新增 `toggleNutFoldRange(folds, open, close)`）：编辑器持有独立状态 `nutFolds`，为区间集合 `[{ open, close }]`（0 基真实行号，含端点、与文本解耦）；归一化规则——按开行升序排序；新区间若被已有区间包含则不重复登记；新区间若包含已折叠子区间则原子区间被吸收。
- 折叠视图（`src/utils/pvfNutFormat.js` 新增 `buildNutFoldLines(text, folds)`）：返回可见行描述 `[{ line, no, folded }]`（`line` 为 0 基真实行号、`no` 为 1 基原始显示行号、`folded` 标记折叠起始行）；**区间起始行与闭括号行均保留**——起始行标记 `folded: true`（渲染时行尾追加 `⋯`），闭括号行按普通可见行输出，仅开闭行之间的行不输出；行号取原始行号，折叠后跳号。**`folded` 判定为「该行是否为某个已折叠区间的开行」**（而非「首个命中区间的开行」）：`} else {` 这类双重角色行既是前块闭行、又是后块开行，两块同时折叠时该行仍可见且必须带 `folded` 标记（行尾 `⋯` 可展开后块）——2026-09-11 修正，此前按「首个命中区间」判定会漏掉其开行身份，导致后块只能从 gutter 箭头展开、正文 `⋯` 缺失（对照 VS Code：占位符跟随该行所开的折叠区间产生）。
- Gutter 折叠标记（`src/utils/pvfNutFormat.js` 新增 `buildNutGutterMarks(rows, foldableLines, folds, hovered)`）：按行给出**语义标记** `{ line, no, mark }`，`mark` 取 `"collapsed"` / `"expanded"` / `""` 三值（不返回字符字形，字形由展示层决定，避免工具层耦合渲染细节），严格对照 VS Code 默认「鼠标悬停才显示」的折叠控件行为——**已折叠**区块的起始行常显 `collapsed`（VS Code 折叠态箭头不随鼠标隐藏）；**未折叠**的可折叠行仅当 `hovered` 为真（鼠标位于左侧 gutter 区域）时给出 `expanded`，否则为空标记；非可折叠行为空标记。空标记仍渲染为固定宽度占位，保证折叠标记显隐不改变行号列宽与行高。
- **Gutter 版式：行号在左、折叠箭头在右（2026-09-11 修正，VS Code 源码核对结论）**：VS Code 的 gutter 横向顺序为 **行号 → 折叠箭头 → 正文**，箭头位于**行号右侧**、紧邻正文，而非行号左侧。依据（VS Code 源码 `src/vs/editor/common/config/editorOptions.ts` 的 `computeLayout` 与 `LinesDecorationsOverlay` / `LineNumbersOverlay`）——① 横坐标计算为 `lineNumbersLeft = glyphMarginLeft + glyphMarginWidth`、`decorationsLeft = lineNumbersLeft + lineNumbersWidth`、`contentLeft = decorationsLeft + lineDecorationsWidth`，即装饰槽位整体位于行号右侧、正文左侧；② 行号经 `LineNumbersOverlay` 以 `left: lineNumbersLeft` 绝对定位，折叠箭头经折叠装饰提供器（`FoldingDecorationProvider` 的 `firstLineDecorationClassName`）与 `linesDecorationsClassName` 落在同一条 `LinesDecorationsOverlay`（`left: decorationsLeft`）上；③ 折叠开启时 `lineDecorationsWidth += 16`，即箭头占 16px 定宽槽位。本仓据此把 gutter 行渲染顺序定为 **`行号 + 箭头图标列`**（此前误置于行号左侧，2026-09-11 修正），箭头列取 **16px** 定宽（对齐 VS Code 的 16px 槽位；`flex-shrink: 0`，文本右对齐时箭头恒为 gutter 最右侧一列，行号数字整体右对齐于其左）。
- 渲染观感对照（VS Code / code-server）：折叠标记列渲染为**自绘 SVG 折叠箭头图标**（16×16 viewBox、`fill="none"` + `stroke="currentColor"` 折线几何，「已折叠」为右向 chevron、「未折叠」为下向 chevron；几何自绘，不内嵌第三方图标字体或资产），图标盒 16px 见方（内联盒高 16px 小于 gutter 行高，不改变行高），箭头显隐不引起 gutter 重排；折叠占位符 `⋯` 取 VS Code 同款灰色（`--text-muted`，常态 `opacity: 0.7`、悬停 `1`，`cursor: pointer`）；折叠区块起始行在折叠视图中以低透明度底色（`--bg-2`）标示。整体观感对照 VS Code 编辑器（code-server 为其开源服务端包装，编辑器渲染语义同源：行号右侧箭头列 + 悬停显隐 + 可点击占位符），配色仍由本仓主题变量决定，不整体替换编辑器皮肤。
- 渲染接线修正（2026-09-11，问题原因与解决方式）：**鼠标移入左侧 gutter 时列宽抖动**——`.pvf-fold-mark` / `.pvf-fold-ellipsis` 规则写在 scoped 样式块内，而 gutter / 正文经 `v-html` 注入的内容不带组件 scope 属性，scoped 选择器不命中，空标记宽度塌缩为 0、有标记时被字形撑开，gutter 宽度由内容决定（`flex-shrink: 0`）因而随悬停变化；解决方式为对注入内容一律使用 `:deep()`（与既有 `:deep(.pvf-folded-line)` 写法一致），并把标记列与图标盒固定为 **16px**（对齐 VS Code 的 16px 装饰槽位），列宽恒定。同一缺陷在文档中的另一处旧表述曾写作「标记列固定 1em、图标盒固定 1em」，与实现（16px）矛盾，已删除；定宽槽位必须用绝对单位——`1em` 随字号变化，不满足「箭头显隐不引起列宽 / 行高抖动」的要求。
- 渲染与交互（2026-09-11 **「折叠态可编辑」修正**，对齐 VS Code 语义）：有折叠时编辑器仍使用**单一可编辑文本模型**——`editText` 始终保存完整文本（不含占位符、不被折叠改写），折叠只是显示层状态。折叠视图由三层构成：gutter（按 `buildNutFoldLines` 的可见行渲染、原始行号跳号）、高亮正文层（`<pre>`，只渲染可见行、`pointer-events: none`）、以及覆盖其上的**折叠态 textarea**（取值为可见行文本）。三层共用同一条 `.pvf-code-highlight, .pvf-code-textarea` 版式规则（同 padding / 字号 / 行高 / tab-size），可见行逐行对齐；textarea 可正常输入、选区与移动光标，**非折叠区的行照常可编辑**，被折叠隐藏的行在展开前不可编辑（对齐 VS Code：整个文档是同一个可编辑文本模型，折叠仅隐藏视图，隐藏期间其内容不可修改）。此前版本为「有折叠即切到只读 `<pre>` 视图（无 textarea）」，会导致**整个文件**不可编辑，与上述语义不符，本次修正。
- 折叠态编辑合并（`src/utils/pvfNutFormat.js` 新增 `mergeNutFoldEdit(text, folds, nextVisibleText)` 与 `buildNutFoldEditableText(text, folds)`）：折叠态 textarea 的输入按行做**前缀 / 后缀公共段差分**，定位被改动的真实行区间，用编辑结果替换该区间、其余行原样保留（未涉及行字节不变、行尾风格沿用源文件主流行尾），同时按行数差平移折叠区间——区间整体在替换区之后则整体平移，开行 / 闭行落在替换区内则钉到替换区边界，返回 `{ text, folds, blocked, expand }`；并回后再以 `buildNutFoldEditableText` 自校验「按新区间取出的可见行文本 == 用户输入」，不自洽一律按保护处理。
- 折叠区间保护（**避免隐藏内容被误删**，本仓有意差异）：textarea 只含可见行，折叠区间的开行与闭行在 textarea 中相邻，因此「在边界处换行 / 退格」在真实文本中是跨越隐藏区的行级改动。此类改动（会把新行插入隐藏区内部，或把隐藏行纳入替换区）不直接执行：`mergeNutFoldEdit` 置 `blocked` 并给出需展开的区间（`expand`），组件回退本次输入并**展开相应折叠区间**，由用户在展开后的完整文本上继续操作。选择整段跨折叠区删除同理先展开、不静默丢弃隐藏内容（VS Code 会直接删除选区内的隐藏文本，本仓选择先展开以杜绝误删，登记于 §5）。
- 折叠占位符交互层：`⋯` 不再渲染在高亮正文层内（该层在折叠态为纯展示、不接收鼠标事件），改由**覆盖层**（`.pvf-fold-markers`）渲染——锚点由 `src/utils/pvfNutFormat.js` 的 `buildNutFoldMarkerAnchors(rows, lines, tabSize)` 给出（纯函数：按折叠视图可见行输出 `{ line, row, column }`，`row` 为视图行序、`column` 为**行末之后一格**的可见列 = 行可见宽度 + 1，制表符按 4 列折算），展示层按 `x = 左内边距 + (column - 1) × 字符宽`、`y = 上内边距 + row × 行高` 换算像素位置；层容器 `pointer-events: none`、仅占位符自身 `pointer-events: auto`（`cursor: pointer` + `data-line`），点击经 `onNutFoldBodyClick` 展开对应区块；覆盖层 z-index 高于折叠态 textarea（否则会遮住正文无法编辑）。折叠视图中右向箭头（常显）与行尾 `⋯` 均可点击展开，鼠标移入 gutter 时未折叠的可折叠行显示下向箭头可继续折叠其它区块，工具栏提供带图标的「展开全部」。
- **占位符覆盖层裁剪修正（2026-09-11，缺陷修复；两面结构对齐装饰覆盖层）**：原实现把**跟随滚动的反向平移 `transform` 与 `overflow: hidden` 放在同一个元素**上——`overflow` 裁剪在元素自身坐标空间内生效，而 `transform` 把该元素的框（连同裁剪窗口）一起平移，于是裁剪窗口随内容移动而非固定在编辑区视口，**只有首屏内容范围内（视图行序 × 行高 ≲ 编辑区高度）的占位符能被绘制**，其余折叠行的 `⋯` 一律不绘制（表现为「折叠行有整行底色、gutter 有箭头，唯独 `⋯` 缺失」）。解决方式：拆成与 `.pvf-code-decor` 同款的两面结构——外层 `.pvf-fold-markers` 只负责**固定视口裁剪**（`inset: 0` + `overflow: hidden` + `pointer-events: none`，**不带 transform**），内层 `.pvf-fold-marker-scroll` 承载反向平移（`transform: translate3d(calc(-1 * var(--decor-x, 0px)), calc(-1 * var(--decor-y, 0px)), 0)`，随 `decorScroll` 同步），占位符位于内层；裁剪窗口固定在编辑区，占位符随内容平移，任意滚动位置均可绘制。同时修正锚点列的**末字符重叠**：原式 `(_nutVisibleColumn(raw, raw.length) - 1) × 字符宽` 取的是最后一个字符格的左边界（`⋯` 叠在末字符上），现取行末之后一格再叠加 6px 内边距，形态与 VS Code 行尾占位符一致（`{` 与 `⋯` 之间留出空隙）。静态守卫断言「裁剪层不带 transform、平移层独立存在」，见 §4 表。
- 折叠态光标与滚动：折叠态 textarea 为滚动容器，滚动时同步高亮正文层 / gutter / 装饰覆盖层；光标 / 选区偏移单独存放（`nutFoldCaretStart` / `nutFoldCaretEnd`，沿用编辑态偏移域会与可见行偏移错位），经 `_nutFoldOffsetToDoc` 按可见行描述映射回全文偏移供装饰层绘制当前行与同类词，进入折叠视图时置未同步（−1）不绘制。
- **折叠切换保持视口锚点（2026-09-11 修正，缺陷修复：不跳回顶部）**：编辑视图与折叠视图是 `v-if` / `v-else` 两棵**互斥子树**，首次折叠（或「展开全部」回到编辑态）会整体替换编辑区 DOM，新滚动容器（textarea）的 `scrollTop` 从 0 开始；原实现的折叠后处理只把新容器的滚动量**同步**给高亮层 / gutter（`syncScroll` / `onNutFoldScroll`），**没有恢复视口位置**，因此在 200 行以后折叠时视口会跳回文件顶部（折叠状态与文本无关，属纯展示层缺陷）。解决方式：折叠状态变更**前**记录视口锚点，变更后按锚点还原——① 锚点 = 「视口顶部对应的**真实行号** + 行内像素偏移」（`captureNutScrollAnchor(rows, scrollTop, paddingTop, lineHeight)`，`rows` 为折叠态可见行描述 `nutFoldView`、编辑态传 `null` 走**恒等映射**（行号即视图行序，避免为大文件构造全行描述）；由 `row = ⌊(scrollTop − 上内边距) / 行高⌋` 取行、偏移取该行内余量）；② 还原 = 在新可见行集合里把锚点行映射回视图行序（`resolveNutScrollTop(rows, anchor, paddingTop, lineHeight)`：**精确命中该行** → 用其视图行序；该行因本次折叠被隐藏 → 退到其**之前**最后一个可见行（内容上方保持不动，不向下跳）；锚点行早于全部可见行 → 取首行），再赋回 `scrollTop`；③ 三个变更入口（gutter 箭头 / `⋯` 点击折叠、`⋯` 点击展开、工具栏「展开全部」）统一先取锚点、`$nextTick` 后恢复，再同步各层。因锚点落在**真实行号**上而非视图行序，折叠区间上方的展开 / 折叠（可见行数变化）不会让视口漂移。
- 语义边界：折叠本身不改写文件字节、编码分支判定与脏态（`nutFolds` 与 `editText` 解耦，仅切换视图，折叠 / 展开不进入脏态）；**折叠态下的实际编辑**与其他编辑一样写回 `editText` 并进入脏态（用户改动应当可保存）。保存链路在完整文本上操作、无需先展开；工具栏「格式化」仍先清空 `nutFolds` 回到编辑态再重排（保持既有已登记行为）。折叠态下 Tab 缩进、悬浮提示与代码引用点击等编辑态辅助交互暂不接线（textarea 只承载可见行，字符偏移与全文不一致），登记于 §5；大文件只读预览模式不提供折叠（折叠依赖编辑态逐行渲染）。
- 已知限制：折叠区间按花括号配对、不跨 switch 语义分组（规则与格式化一致）；折叠态编辑的区间平移按行数差计算（同 VS Code 的行号跟随），同一行内的字符级增删不影响区间；跨折叠边界的行级编辑先展开区间（见上条保护策略）。
### 3.6 编辑器装饰语义（2026-09-11，折叠整行底色 / 缩进辅助线 / 同类词高亮，参照 VS Code 编辑器）

对照对象为 VS Code 编辑器默认设置下的渲染语义（code-server 所服务的前端即 VS Code，其仓库自身无编辑器渲染实现，见 §3.4）。下列语义取自 VS Code 源码事实（文件与标识符级依据逐条列出），本仓按同等语义落地，**全部为展示层新增：不改动文本模型、不进脏态、不影响保存链路**，且仅在 `.nut` 代码编辑器（`highlightMode === 'nut'`）生效。设置默认值依据 `src/vs/editor/common/config/editorOptions.ts`。

- **折叠区整行底色**：VS Code 对折叠区间使用整行装饰（折叠装饰提供器：`isWholeLine: true`、样式类 `folded-background`，见 `src/vs/editor/contrib/folding/browser/foldingDecorations.ts`；样式 `src/vs/editor/contrib/folding/browser/folding.css` 的 `.monaco-editor .folded-background`），底色覆盖**整行行宽**而非文本宽度；底色为半透明（默认 `editor.foldBackground` = 选区底色 30% 透明度），折叠区间内被隐藏的行不渲染，可见的折叠起始行因而是整行底色 + 行尾 `⋯`（`afterContentClassName: 'inline-folded'`，字符 U+22EF、`cursor: pointer`，颜色 `editor.foldPlaceholderForeground` 默认 `#808080`）；折叠高亮受 `editor.foldingHighlight` 控制（默认 `true`）。
- **本仓修正（2026-09-11）**：此前以行内 `<span>` 包裹整行文本承载底色，底色只覆盖文本宽度（视觉上随行内容长短变化，与 VS Code 不符）。现改为在**装饰覆盖层**按可见行渲染左右贯通整行的矩形，颜色取本仓主题色半透明（`color-mix(in srgb, var(--accent) 12%, transparent)`，回落 `rgba(91, 140, 255, 0.12)`；VS Code 的 `editor.foldBackground` 由选区底色降透明度而来，本仓同取低透明度强调色）。
- **缩进辅助线（2026-09-11 修正：区块区域辅助线，用户规则）**：VS Code 默认辅助线（`editor.guides.indentation: true`）由模型层 `getLinesIndentGuides`（`src/vs/editor/common/model/guidesTextModelPart.ts`）按**缩进列**给出——有内容行取 `ceil(缩进列 / indentSize)`，纯空白行由上下最近有内容行推算（同文件 `_getIndentLevelForWhitespaceLine`），渲染层（`src/vs/editor/browser/viewParts/indentGuides/indentGuides.ts`）按可见行输出绝对定位竖线元素（宽为一个空格宽、`box-shadow: 1px 0 0 0 var(--guide-color) inset` 画 1px 线、高度 = 行高、逐行拼接），列位置为 `indentGuide = (indentLvl - 1) * indentSize + 1`（即 `leftOffset + (visibleColumn - 1) * spaceWidth`）。**本仓按用户给定规则改为「区块区域辅助线」**：辅助线只由**跨行 `{}` 区块**产生，某区块的辅助线只绘制在其**区域内部行**上——「开括号行的下一行」至「闭括号行的前一行」（与折叠配对的区间语义同源：字符串 / verbatim / 注释内花括号不参与配对，同行 `{}` 不产生区域，相邻开闭行即无内部行亦不产生），逐行层级 = 该行所在跨行花括号区块的嵌套数（区块内部行区间差量累加，`computeNutBlockGuideLevels`）。列位置取区块体缩进边界 `(层级 - 1) × 一级缩进宽 + 1`，与 VS Code 缩进辅助线的列几何一致（原实现取 `层级 × 一级缩进宽`，深一层辅助线恰好压在行首文字上）。由此：单行展示的语句（含同行 `if (...) return ...;`）不自带辅助线；未由花括号开出的缩进（悬挂单语句体、条件续行、`case` 体内更深一层缩进等）不产生辅助线；区域内部空白行保持辅助线连续。
- **活动缩进块高亮**：由 `getActiveIndentGuide`（同 `guidesTextModelPart.ts`）给出光标所在块的内层辅助线（返回行范围 + 层级），并含两处特判——光标位于**开括号行**（下一行层级 = 当前层级 + 1）时活动块取**子块**辅助线；光标位于块尾（上一行层级 - 1 = 当前层级）时取**父块**辅助线；层级为 0 时不再延伸。活动辅助线以更强的 `--guide-color-active` 着色（`indentGuides.ts` 的 `indent-active`）。本仓 `findNutActiveIndentGuide` 的输入即上述区块层级数组（`computeNutBlockGuideLevels`），语义与两处特判一致。
- **同类词高亮（光标处 / 选中词的全部出现处）**：默认 `editor.occurrencesHighlight: 'singleFile'`、`editor.occurrencesHighlightDelay: 0`、`editor.selectionHighlight: true`。无语言服务时的**文本型路径**（`src/vs/editor/contrib/wordHighlighter/browser/textualHighlightProvider.ts`）：取光标（或选区起点）处的词——词定义 `DEFAULT_WORD_REGEXP`、位置判定 `matchIndex <= pos && lastIndex >= pos`（**光标紧邻词首 / 词尾同样命中**，`src/vs/editor/common/core/wordHelper.ts`）；再以「区分大小写、非正则、`USUAL_WORD_SEPARATORS` 整词边界」在全文件查找匹配。装饰类为 `wordHighlightText`（`src/vs/editor/contrib/wordHighlighter/browser/highlightDecorations.ts` + `highlightDecorations.css`），默认深色 `#575757B8`；有非空选区时以选区同类色（`editor.selectionHighlightBackground`，选区底色 30% 透明度、类规则再乘 0.5）呈现。
- **选区门控**（`src/vs/editor/contrib/wordHighlighter/browser/wordHighlighter.ts` 的 `_run`）：**多行选区不参与**；选区须落在同一个词内或恰好包住一个词（`word.startColumn <= 选区起 && 选区止 <= word.endColumn`）；选区长度上限 `editor.selectionHighlightMaxLength`（默认 200 字符，0 为不限）。
- **本仓落地**：工具层新增 `findNutWordOccurrences`（同款词提取 + 整词边界全文件匹配，**纯文本匹配**——注释 / 字符串内的同名单词同样命中，与 VS Code 文本型路径一致，不做语义过滤）；展示层在装饰覆盖层以矩形绘制于**文字之下**。光标 / 选区取自 textarea 的 `selectionStart` / `selectionEnd`。光标处词与选中词底色同取 VS Code 深色默认 `#575757B8`（本仓 `rgba(87, 87, 87, 0.72)`），选中词另加 1px 边框，对应 `wordHighlightStrong` 以边框区分强弱的默认呈现。装饰矩形规模门控：文本超过 20 万字符时仅保留折叠整行底色与当前行整行矩形（矩形数与行数同阶），不再构造缩进辅助线与同类词矩形，避免超大文本下装饰元素数量随行数 × 层级膨胀。
- **当前行高亮**：默认 `editor.renderLineHighlight: 'line'`、`editor.renderLineHighlightOnlyWhenFocus: false`。VS Code 以整行元素的 1px 边框呈现（`editor.lineHighlightBorder`，深色默认 `#282828`；`editor.lineHighlightBackground` 默认 `null`，不填充）。本仓以装饰覆盖层渲染整行 1px 边框矩形（不填充），并随纵向滚动同步。
- **绘制层次**：装饰（折叠整行底色 / 缩进辅助线 / 同类词矩形 / 当前行边框）绘制于**文字之下**（VS Code 同为装饰先绘制、字形后绘制），故高亮层正文背景改为透明、编辑器底色由容器承载；覆盖层与编辑器同为 `pointer-events: none`，不夺取 textarea 的鼠标、选区与光标行为。
- **列坐标约定**：装饰几何一律以**可见列**（1 基，制表符按 `tab-size: 4` 折算）表达，展示层按等宽字体 `x = 左边距 + (可见列 - 1) × 字符宽` 线性换算；工具层与测试亦按可见列断言。
- **行坐标约定（2026-09-11 修正：整数固定行高）**：装饰矩形的纵坐标由 `getEditorMetrics()` 以 `paddingTop + 行序 × lineHeight` 线性换算，而正文行盒位置由浏览器排版决定，两者必须取同一数值才能逐行对齐。原实现四处（`.pvf-code-highlight` / `.pvf-code-textarea` 正文层、`.pvf-gutter-pre` 行号层、`.pvf-code-decor` 装饰层、装饰矩形 `height`）取相对行高 `line-height: 1.6`，在 `font-size: 0.8rem`（根字号 16px → 12.8px）下为 **20.48px**（非整数）：`getComputedStyle().lineHeight` 回报 20.48px，而浏览器排版按 LayoutUnit（1/64px）取整后实际逐行推进 **20.46875px**，每行相差 **0.01125px** 并线性累积——1000 行约 11px、2000 行约 22px；表现为行号越大装饰矩形越偏低（同类词背景相对文字逐行下移、文字显得偏上），即「前部分居中、后续偏上」的现象。解决方式：编辑器行网格改为**整数固定行高 20px**，以 CSS 变量 `--nut-editor-line-height` 定义于 `.pvf-code-editor`，上述四处（含装饰矩形高度）共用同值——整数像素在 1/64 网格上精确可表示，逐行推进恒等于 20px，与 JS 换算完全一致。按 LayoutUnit（1/64px）网格推算即可复核：`20.48px` 的相对行高排版推进被取整为 `20.46875px`，每行误差 `0.01125px`、1999 行累计漂移 `22.49px`（表现为行号越大装饰矩形越偏低）；整数 `20px` 在 1/64 网格上精确可表示，逐行推进恒为 `20px`、无累计漂移（余下仅字形盒相对行盒的常量半行距，文字仍在矩形内居中）。20px 与大文件虚拟滚动既有常量 `LARGE_VIRTUAL_LINE_H = 20`（`.pvf-largefile-cline` / `.pvf-largefile-gline` 的 `height` / `line-height: 20px`）一致；`getEditorMetrics()` 的行高回落值同步改为读取该 CSS 变量（缺省 20px），不再回落 `fontSize × 1.6`（相对行高会重现非整数漂移）。**有意差异（登记 §5）**：固定 px 行高不随根字号缩放，本仓取「装饰与文字严格对齐」优先于「行高随 `rem` 缩放」。
- **已登记差异（VS Code 默认有、本仓未实现）**：代码缩略预览 / minimap（用户明确排除，不在对齐范围）；匹配括号高亮（`editor.matchBrackets` 默认 `'always'`，需按括号类型配对与包围括号对判定）；粘性滚动（sticky scroll）；多文件同类词高亮（`'multiFile'`）与语义读写区分（需语言服务，本仓走文本型路径）。另外**括号对辅助线**（`editor.guides.bracketPairs`，彩色、按括号列锚定 + 开闭行横向段）在本版 VS Code 中默认值为 `false`（`GuideOptions` 默认 `{ bracketPairs: false, bracketPairsHorizontal: 'active', highlightActiveBracketPair: true, indentation: true, highlightActiveIndentation: true }`），该彩色括号对辅助线本仓未实现；但其**区间语义**（只对跨行括号对、只在开闭行之间的内部行绘制）已由本仓区块区域辅助线规则采用（见上「缩进辅助线」条），登记备查。
- **辅助线语义差异（登记，用户规则）**：VS Code 默认缩进辅助线按**缩进列**给出（悬挂单语句体、条件续行、`case` 体内更深一层缩进等同样产生辅助线）；本仓按用户规则改为**区块区域辅助线**，只对跨行 `{}` 区块的区域内部行绘制，无花括号开出的缩进不产生辅助线。列位置仍与 VS Code 缩进辅助线几何一致（`(层级 - 1) × 一级缩进宽 + 1`）；一级缩进宽取 `detectNutIndentUnit` 检测到的文件缩进单位（tab 记 4 列、空格按检测宽度），与「格式化」输出层级一致，此为有意差异。
