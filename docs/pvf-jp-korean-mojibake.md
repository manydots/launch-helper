# PVF 韩文乱码修复方案（JP / 86JP）

## 1. 问题现象

`C:\Users\Administrator\Desktop\PVF\86JP\Script.pvf`（格式识别为 **JP / original**，sTrA 全局编码自动探测为 **gbk**）的 `npcname.lst`、`monstername.lst`、`aicharactername.lst`、`passiveobjectname.lst`、`skillname0~10.lst` 等 .lst 文件中，NPC 名 / 怪物名 / 技能名出现「汉字乱码」（实际为未翻译韩文被双重转码）：

```
`菜 阜腮 粮` 34
`肺历 饭后` 29
`箕老废 绊喉赴靛` 9
`绊喉赴` 1
```

要求：同 90US 修复方式，**不切换整个文件编码**，让这些文本恢复为正常韩文。

## 2. 根因分析（已用实际文件字节验证）

- 乱码**全部位于 sTrW（UTF-16 字符串表）**：全表 205019 条中 204930 条含 CJK，乱码集中在偏移 4380000~4383000 连续区（技能名 / NPC 名 / 地名等，均为汉化版未翻译部分）；sTrA（128 万条）CJK 条目 0，无需改动。
- 存储链路（与 90US 的 CP437 链路不同，本文件为 GBK 链路）：
  ```
  韩文 EUC-KR/CP949 字节 → 按 GBK 解码成汉字乱码 → 按 UTF-16LE 写入 sTrW
  ```
- 例：偏移 4382180 的 `肺历 饭后`，`肺`=GBK B7CE、`历`=C0FA、`饭`=B7B9、`后`=BAF3；
  以 EUC-KR 解码 `B7CE C0FA B7B9 BAF3` = `로저 레빈`。
- 正常中文（如 `破旧的绸缎护肩`）与乱码**混存于同一张表**，乱码区前后紧邻正常中文条目（如偏移 85510 `卡妮娜` 与 85856 `飞盘 3`），故不能按偏移区域粗粒度判定。

## 3. 恢复链路（已用真实字节验证）

```text
sTrW UTF-16 字节
  → UTF-16LE 解码          → 得到汉字乱码文本 T
  → 按 GBK 反向编码        → 得到原始 EUC-KR 字节
  → EUC-KR 解码            → 得到正确韩文
```

## 4. 判定规则设计（自测历程，数据驱动收敛）

GBK 的 B0~C8 区（GB2312 一级汉字前 25 行）与 EUC-KR 韩文音节区**字节双射同构**，任何该区的正常中文串经「GBK 编码 → EUC-KR 解码」也必然得到全音节串，故不能只凭字节链路判定。逐版统计（sTrW 全表）：

| 规则版本 | 命中数 | 结论 |
|----------|--------|------|
| v1：汉字 GBK 前导 ∈ B0~C8 + 全音节 | 58368 | **大量误判**：`爸爸`/`你好`/`龙人`/`卡妮娜`、`破旧的绸缎护肩`→`팎앉돨놉뙨빱쇘` 等 |
| v2a：v1 + 排除中文标点 + **含空格** | 20207 | 抽样全部为**可读韩文**（零误伤），空格=韩文分词特征 |
| v2b：v1 + 排除标点 + 无空格短词（≤4 字） | 2271 | 绝大多数误判：`卡妮娜`→`엥콜컹`、`洛兰`→`쭤읊`、`剑魂`→`숲산` |
| v3：无空格短词 + 邻域（±1024B）内有乱码 | 1578 | 仍大量误判：`卡妮娜`(85510) 与 `飞盘 3`(85856) 相邻即命中 |

**信息论限制**：无空格短词（如 `父柳`→`만진`）与正常中文（如 `龙人`→`질훙`、`爸爸`）在字节层面完全同构，**无法在字符串表层面可靠区分**。因此在全局字符串表采用保守的**含空格规则**（v2a）。

**名字型 .lst 行内激进恢复**：对游戏内**名字型 .lst**（NPC/怪物/技能/被动技能名表），逐表统计证明其**不含任何正常中文**（全表扫描分类，见下表），因此对这些文件的行内名字可放宽为**无空格激进规则**：

| .lst 文件 | 条目 | 英文 | 韩文(已恢复) | 疑似韩文(B0C8) | 中文高危 | 中文(B0C8) | 判定 |
|-----------|------|------|------|------|------|------|------|
| npcname.lst | 104 | 6 | 38 | 60 | **0** | **0** | 纯韩文 |
| monstername.lst | 512 | 0 | 324 | 188 | **0** | **0** | 纯韩文 |
| aicharactername.lst | 104 | 0 | 96 | 8 | **0** | **0** | 纯韩文 |
| skillname0~2,4~10.lst | 各 100~440 | 0 | 大多数 | 52~90 | **0** | **0** | 纯韩文 |
| skillname3.lst | 438 | 0 | 376 | 52 | 8* | 2* | 带标点韩文（漏恢复、不误伤） |
| passiveobjectname.lst | 1972 | 86 | 1432 | 438 | 14* | 2* | 带标点韩文（漏恢复、不误伤） |
| itemname.lst（行内） | 10695 | 0 | 9911 | 782 | 2* | 0 | **纯韩文（含 2 条谚文汉字标注）→ 入白名单** |
| itemname.lst（[name] 追加） | — | — | — | — | — | — | 正常中文（`破旧的绸缎护肩`），**不走行内恢复路径** |

> *标着 `*` 的「中文高危」条目（如 `眉捞舷- 气`→`체이스- 기`、`畴胶付捞扁嫡 焊`→`노스마이 기둥 基`、itemname 的 `绞巩磊档 - 磊(砗)`→`십문자도 - 자(者)`）经人工核对**仍为韩文乱码**，仅因含全角标点/连字符/谚文汉字导致 euc-kr 解码含非音节字符而落入该分类；激进规则对它们**拒绝恢复（保持原样）但不误伤**（谚文汉字标注类经 allowKsc 恢复，见下）。
>
> itemname.lst 行内名字二次全量分类（10695 条）：无汉字 9911（正常韩文，如 `(구)1 ~ 10레벨 가죽 방어구 레가시`）+ 全 B0~C8 乱码 782（`(备)碍锋肯`→`(구)강룡완`）+ 含 C9~F7 前导 2（谚文汉字标注 `십문자도 - 자(者)`）——**0 条正常中文**；正常中文物品名（`破旧的绸缎护肩`）来自 .equ 的 `[name]` 标签追加（`extractNameTags` 路径，不走行内恢复），故 itemname.lst 可安全入白名单。

**最终判定规则（两层，`_recoverKoreanFromGbkText(text, requireSpace, allowKsc)`）**：

- **字符串表全局（decodeKoreanMojibakeUtf16 / decodeKoreanMojibake）**：`requireSpace=true, allowKsc=false`
  1. 串含 ≥1 汉字（U+4E00~9FFF），且所有汉字 GBK 前导字节 ∈ **B0~C8**（实测确认 EUC-KR 韩文音节区为 B0~C8，C9 起为 PUA / KSC 汉字区）。**此边界不可放宽**：实测放宽到 B0~F7 会使 22324 条含 CA~F7 汉字的正常中文句（`是`/`成` 等）被误恢复；含扩展 A 区汉字（U+3400~4DBF）直接拒绝；
  2. **串含任何 Hangul 字符（音节/谚文字母/兼容字母/扩展区）直接拒绝**——「存在韩文即韩文模式」：含韩文字符的串必是正规韩文文本（如 90US 内嵌 `改`/`赤`/`美人`），恢复会破坏它；真乱码串（86JP）必然不含韩文字符，检查作用于恢复前文本，两条链路互斥自洽；
  3. 串**含词间空格**（`/\s/`）；
  4. 整串 GBK 编码 → EUC-KR 解码后，非 ASCII 字符**全为韩文（音节/谚文字母/兼容字母）或 CJK 汉字**（允许韩文文本内嵌谚文汉字标注，如 `체이서 : 화(火)`）且至少一个音节；**恢复结果含 `%` 或换行直接拒绝**（中文属性文本特征：`攻击力 +8%%`、`成长胶囊 (1%%)`、多行属性串，86JP 实测误伤 358 条，韩文乱码恢复结果不含二者）。
- **名字型 .lst 行内名字（decodeLstWithNames 路径，白名单文件）**：`requireSpace=false, allowKsc=true`
  - 去掉第 3 条空格要求（激进），恢复无空格短词乱码（`绊喉赴`→`고블린`、`父柳`→`만진`、`(备)碍锋肯`→`(구)강룡완`）；
  - 汉字前导放宽到 **B0~F7**（allowKsc），恢复韩文文本内嵌的 KSC 谚文汉字标注（`체이서 : 공(無)`、`십문자도 - 자(者)`）——行内名字纯韩文，放宽安全；
  - 恢复结果放行**韩文装饰符号**（♡★☆†‡≠≮≯ 带圈数字 ①~⑳ ⒈~⒛，`KR_DECO_SYMBOL_RE`），恢复 `던파♡해피빈`、`☆GBL교 명예 신도☆` 类装饰文本——同样仅行内路径放行。

## 5. 实现方案

### 5.1 `src/utils/gbkEncoder.js`

- 导出 `gbkCode(ch)`：单字符 GBK 编码查询（16 位码，高字节为区号），供预筛逐字符判定，避免整串编码开销。

### 5.2 `src/utils/encoding.js`

- `NON_SYLLABLE_NON_ASCII_RE`：`[^\x00-\x7f\uAC00-\uD7A3]`（非 ASCII 且非韩文音节）。
- `NON_CJK_NON_HANGUL_RE`：`[^\x00-\x7f\uAC00-\uD7A3\u3130-\u318F\uF900-\uFAFF\u3400-\u9FFF]`（非 ASCII 且非韩文且非 CJK 汉字，GBK 恢复结果判定用）。
- `KR_DECO_SYMBOL_RE`：韩文装饰符号（`\u2020\u2021\u2260\u226E\u226F\u2460-\u2473\u2488-\u249B\u2605\u2606\u2660-\u2667`，即 †‡≠≮≯ ①~⑳ ⒈~⒛ ★☆ ♡♥♠♦♣ 等），仅行内白名单路径放行。
- 共享实现 `_recoverKoreanFromGbkText(text, requireSpace, allowKsc)` + 两个入口：
  - `recoverKoreanFromGbkText(text)`：`requireSpace=true, allowKsc=false`（字符串表全局，保守，预筛 B0~C8）；
  - `recoverKoreanNameFromGbkText(text)`：`requireSpace=false, allowKsc=true`（名字型 .lst 行内，激进，预筛 B0~F7 + 放行装饰符号）。
- 恢复结果判定链：含 ≥1 音节 → **含 `%`/换行拒绝** →（allowKsc 时移除装饰符号）→ 非 ASCII 全为韩文或 CJK。
- `decodeKoreanMojibakeUtf16(bytes)`（sTrW）：UTF-16LE 解码 → CP437 链路（90US）→ **GBK 链路（新增，含空格规则）** → 原样兜底。
- `decodeKoreanMojibake(bytes, encoding)`（sTrA）：主解码 → CP437 文本恢复 → **GBK 文本恢复（新增，防御性）** → UTF-8 文本恢复 → 原始字节直解。

### 5.3 `src/utils/pvfTool.js`

- `decodeLst(data, opts)`：新增 `opts.looseNames`；`_fmtBacktickStr(value, loose)` 与 token 5/6/7 的字符串解析在白名单开启时改用 `recoverKoreanNameFromGbkText`（token 3 普通字符串保持原逻辑）。
- `decodeLstWithNames(file)`：`this.decodeLst(data, { looseNames: this._isLooseNameLst(file) })`。
- 新增 `_isLooseNameLst(file)`：文件名白名单 `/^(npcname|monstername|aicharactername|passiveobjectname|itemname|skillname\d*)\.lst$/i`（itemname 经行内 10695 条全量分类证明纯韩文后加入）。

- 乱码条目与 86JP 相同，全部位于 **sTrW**（如 `奔扼切胶,倔绢磷篮八荤` 位于 idx 29252，
  原始字节 `54 59 7C 62 07 52 F6 80 2C 00 14 50 ...`），经 GBK 反向编码 → EUC-KR 解码
  链路可完整恢复为韩文（`굴라학스,얼어죽은검사`、`샤스라`、`번드피닉스`）。
- 行内激进恢复依赖 `_isLooseNameLst` 白名单，其正则匹配 `file.name`；
  **JPAG 根目录文件的 `name` 字段带 `./` 前缀**（`./aicharactername.lst`，
  共 17 个根 .lst 受影响，其中 15 个为名字型白名单文件），
  正则 `/^(npcname|...|skillname\d*)\.lst$/i` 不匹配 → 白名单全部失效 →
  行内恢复未启用；而 `fullpath` 字段干净（`aicharactername.lst`），与 86JP 一致。
- 其余版本不受影响：86JP / 90CN / 90US 的根 .lst `name` 均无 `./` 前缀（白名单 15/15 命中）。

### 8.3 解决

- `PvfArchive._isLooseNameLst(file)` 判定基准由 `file.name` 改为
  **`file.fullpath || file.name`**（fullpath 为归档内规范化路径，无 `./` 前缀），
  兼容 JPAG 根目录文件的 `./` 前缀 name 表示；正则本身不变。
- `test/pvf-jp-mojibake-verify.mjs` 的文件查找同步由 `x.name === f` 改为
  `x.fullpath === f`（JPAG 下 name 带前缀会 NOT FOUND），并新增 JPAG 断言段。
