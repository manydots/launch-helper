## 1. 归档数据模型、头部解密与 GRPI 分块管理（archive.go）

### 1.1 归档头部（48 字节，小端 packed）

| 偏移 | 类型     | 字段                         |
| ---- | -------- | ---------------------------- |
| 0    | u32      | 归档魔数（字面值以源码为准） |
| 4    | byte[20] | Guid                         |
| 24   | i32      | FileCount                    |
| 28   | i32      | Padding                      |
| 32   | i32      | BodySize                     |
| 36   | i32      | GroupCount                   |
| 40   | i32      | HashTableSize                |
| 44   | i32      | NameTableSize                |

### 1.2 头部解密与变体探测

- 双变体尝试：guard 变体先对头部 `[24:28)`（仅 FileCount 字段）应用单字节 XOR 掩码（掩码值以源码为准），再整体按头部密钥流解密；非 guard 变体仅解密。逐变体判定以下条件，全部通过才接受：① 解出归档魔数一致；② FileCount / Padding / BodySize / GroupCount / HashTableSize / NameTableSize 全部非负；③ 声明总大小（48 + FileCount×0x18 + HashTableSize + NameTableSize + GroupCount×8 + BodySize）不超过实际数据长度。
- **签名不能单独区分变体**：guard XOR 只触碰 FileCount 字段，两种变体解出的魔数可能相同，必须以区段布局校验联合判定。
- 本仓对应：`pvfTool.js` `_decodeHeaderCandidate` + `_validateHeaderLayout`——候选链 original → guard → protected（CN 变体为 pvfine 所无），同样以「解密 + 魔数 + 布局合法性」判定候选；pvfine 仅 original / guard 双变体。两侧思路一致。

### 1.3 区段布局

```
[头部 48B][文件表 FileCount×0x18][HASH 表][字符串池区][GRPI GroupCount×8][数据区 BodySize]
```

各分区偏移自头部起顺序推导；声明的数据区终点越界即判定文件损坏。

### 1.4 文件表条目（0x18 字节，明文）

每条 6 × u32（小端）：`nameOff` / `pathOff`（字符串池偏移，引用目录与文件名两段）、`chunk`（数据分块索引）、`off` / `size`（chunk 解压后载荷内的位置与长度）、`typ`（数据类型：脚本 / UTF-16 文本）。

### 1.5 GRPI 分块管理

- GRPI 区整段以 GRPI 密钥解密后，为 GroupCount 对 `(compSize, origSize)` i32。
- **compSize 为累积压缩大小**：分块 i 的密文区间 = `[数据区起点 + groups[i-1].compSize, 数据区起点 + groups[i].compSize)`（首组起点 = 数据区起点，即前一组累积值为 0）；`origSize` 为该块解压后大小。
- 分块解压结果按索引缓存（读取幂等，编辑写入走独立 overlay 层）。
- 本仓对应：`pvfTool.js` `_parseGroups` + `_getChunk`——同一累积公式（前一组 `compressedSize` 作起点偏移，已核对一致）；编码侧重封包时同样按累积值回写 GRPI。

### 1.6 内存索引

| 索引           | 语义                                                                                                                                                                                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 路径索引       | 大小写不敏感 `dir/name` 查询。查询键归一化：`\`→`/`、去首尾空白、去 `./` 与 `/` 前缀、去尾部 `/`、转小写；**首见条目优先**（镜像参考 GM 工具行为）。显示路径（`FullPath`）则直接拼接池中原始字符串，不做归一化（条目可能合法包含非常规空白，仅查询键归一化） |
| 字符串解析缓存 | 字符串池偏移 → 文本，O(1) 查表                                                                                                                                                                                                                               |
| 分块缓存       | 分块索引 → 解压结果                                                                                                                                                                                                                                          |
| 编辑 overlay   | 条目索引 → 替换载荷（未落盘的内存编辑），保存时重建分块                                                                                                                                                                                                      |
| 字符串池脏标记 | 池内追加过新字符串后置位，保存时需重建索引结构                                                                                                                                                                                                               |

本仓对应：`_pathIndex`（fullpath → file，懒构建）/ `_strAValueCache` / `_strWValueCache` / `_chunkCache` / `_overlay` 一一对应；本仓另有软删除 / 重命名集合与原始元数据快照，为编辑功能扩展，pvfine 无。

## 2. 脚本反编译：格式化规则与层级嵌套缩进（file.go）

### 2.1 token 流与类型

每 5 字节一 token：`[type:1][i32 小端]`。反编译处理的类型：

| type  | 形态         | 反编译输出                                              |
| ----- | ------------ | ------------------------------------------------------- |
| 0     | 整数         | 十进制字符串                                            |
| 2     | 浮点         | float32 最短 `%g` 表示（Go `FormatFloat('g', -1, 32)`） |
| 3     | 标签         | 整行输出 `[name]` / `[/name]`                           |
| 5 / 7 | 块串标记     | 强制换行后独立行 `{5=\`..\`}`/`{7=\`..\`}`              |
| 6     | 反引号字符串 | `` `text` ``，与数值同样按「值前缀」规则连接            |

未知类型（1、4 等）**静默跳过不输出**。字符串输出统一经反引号转义：`` ` `` → ` ` ``（双写）。

### 2.2 标签解析

`[inner]` 形式且 inner 非空即为标签；inner 以 `/` 开头为**闭合标签**（`[/name]`）。非标签形式的 type 3 token（裸词）在反编译中仍按 type 3 整行输出原文本。

### 2.3 换行规则（tokensPerLine）

两级换行规则，先 section 级后文件级：

| 级别                         | 匹配            | 每行值 token 上限 |
| ---------------------------- | --------------- | ----------------- |
| section 级（按标签名）       | `skill data up` | 7                 |
| section 级（按标签名）       | `skill levelup` | 3                 |
| 文件级（按扩展名，小写匹配） | `.lst`          | 2                 |

- 每个进栈的 section frame 自带行计数器；无 section 级规则的 frame 落到文件级计数器。
- 达到上限时：下一值 token 输出前换行，并将对应计数器清零。同一值 token 只计入一个计数器（section 级规则存在时不计文件级）。
- 标签本身不计入行计数；标签输出时还会将所在 frame 的行计数清零。

### 2.4 层级嵌套栈语义

- **预扫描**：反编译前先全量扫描 type 3 token，收集所有「出现过闭合形式」的标签名集合；仅当开标签名在该集合中才视为**可入栈 section**（无闭合配对的开标签不改变缩进层级，避免病态文件把缩进推深）。
- **入栈**：可入栈的开标签输出后 push frame（记录标签名、firstToken 标志、section 级格式规则、行计数）。
- **出栈**：闭合 `[/name]` 自栈顶向下查找**最近同名** frame，截断至该位置（弹出该 frame 及其上全部 frame）。
- **顶层分隔**：栈空时输出的开标签为顶层 section；已出现过顶层 section 后再遇顶层 section，输出前额外空一行（两个换行分隔，首个顶层 section 前不加）。

### 2.5 缩进计算（Tab 缩进）

缩进单位为 Tab（每层 1 个）。行首值 token 的缩进深度由 `contentIndent` 决定：

```text
contentIndent():
  若文件尚未输出任何内容或标签:            0
  若 section 栈为空:
    文件级 tokensPerLine 存在:             0
    否则:                                  1
  栈深 D = len(stack):
    顶 frame 有 section 级规则 或 该 section 值区尚未输出任何 token:  D
    否则（值区已开始）:                    D + 1
```

要点：

- **标签行缩进 = 输出时栈深**：开标签在 push 之前输出（缩进 = 当前栈深），闭合标签在弹栈之后输出（缩进 = 弹栈后栈深），故闭合与对应开标签左对齐。
- **值区首 token 比标签深一级**（firstToken 时缩进 = 栈深）；首个值 token 之后若该 section 无专属换行规则，值区整体再深一级（D + 1）——形成「标签 / 值块」两级视觉层次。
- 有 section 级 tokensPerLine 规则的 section（如 `skill data up`）值区**不**额外加深，保持 D。
- 同行后续值 token 之间以**单个 Tab** 连接（不做列对齐）；与行首缩进无关。
- 栈空且无文件级规则时，内容固定缩进 1 层；有文件级规则（`.lst`）时内容顶格。

### 2.6 输出形态汇总

| 元素           | 输出行为                                                                      |
| -------------- | ----------------------------------------------------------------------------- |
| type 3 标签    | `[换行]缩进 标签文本 [换行]`；闭合标签先弹栈、顶层 section 前按 §2.4 追加空行 |
| type 0 / 2 / 6 | 行首：写缩进后输出；非行首：前置单个 Tab 同行连接                             |
| type 5 / 7     | 强制换行 → 写缩进 → `{5=\`..\`}`/`{7=\`..\`}` 独立占一行                      |
| 字符串内容     | 内嵌反引号一律双写转义（`` ` `` → ` ` ``）                                    |

### 2.7 再编码互逆（script.go，简述）

反编译文本可再编码回 token 流，规则：`#` 起至行尾为注释；`` `..` `` → type 6（双反引号反转义）；`{5=` / `{7=` 标记 → type 5 / 7（花括号体可为整数或字符串偏移，`}` 配对时尊重反引号段）；`[tag]` → type 3；裸词按整数 → 浮点 → 字符串偏移顺序尝试；空白仅作 token 分隔。**token 流本身不含布局信息**——反编译的换行 / 缩进是展示层产物，再编码时按规则重排，不保留原文本的版式。

## 3. 与本仓实现的对照（差异清单）

| 维度                      | pvfine（file.go）                          | 本仓（pvfTool.js）                                                                          |
| ------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------- |
| 缩进                      | Tab 层级缩进（§2.5），section 嵌套栈       | 无缩进扁平输出（`decodeToken`）                                                             |
| 数值连接                  | 同行值 token 间单个 Tab                    | 连续数字以**空格**合并同行（`_appendNumRun`）                                               |
| `.lst` 布局               | 文件级规则：每 2 个值 token 换行、内容顶格 | 「数字+反引号串」或「反引号串+数字」合并整行、每条独占一行（`decodeLst`）                   |
| section 换行规则          | `skill data up` 7 / `skill levelup` 3      | 未实现（全部数字 token 顺延合并）                                                           |
| 浮点格式                  | Go `%g` 最短表示                           | `float32ToString` 最短往返表示（JS；两者多数值一致，指数记法切换阈值可能存在个别差异）      |
| 顶层 section 空行分隔     | 有                                         | 无（标签行直接相邻）                                                                        |
| 未知类型处理              | 静默跳过                                   | 输出 `?(type,value)` 占位                                                                   |
| UTF-16 文本 mojibake 修复 | TypeUnicode 解码时做 CP437/EUC-KR 修复     | `encoding.js` 同类机制（见 `docs/pvf-jp-korean-mojibake.md` / `pvf-us-korean-mojibake.md`） |
| 头部变体                  | original / guard 双变体                    | original / guard / protected 三变体（CN 扩展）                                              |

结论要点：

1. 两侧**二进制语义层**（头部字段、区段布局、文件表、GRPI 累积分块、字符串池偏移引用、内存索引职责）一致；差异集中在**展示层版式**（缩进 / 换行 / 连接符）与本仓的扩展变体。
2. pvfine 的格式化输出（缩进与换行）是 token 流之上的**展示层样式**，与解码正确性无关；本仓既有解码输出与本仓编码器（按空白拆分重新 tokenize，见 `pvfTool.js` `encodeContent` 一系）保持互逆，不受影响。
3. 如未来需要将本仓脚本展示对齐 pvfine 版式（层级缩进 / 分节换行），按本文 §2 规则实现，并遵循 AGENTS.md「先文档、后自测、再改码」硬性顺序；实现时以权威导出样例逐行核对（§2 规则为参考项目语义，最终以权威样例为准）。
